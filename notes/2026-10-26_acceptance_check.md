## 2. 缺陷 A（**已修**）：`make_table.py` 的"后半程"用的是行数，不是 rollout 数

```python
# 修前  analysis/make_table.py:88
half = max(1, len(rows) // 2)        # len(rows) 是 metric 行数
last_idx = max(rollout_idx)
keep_from = last_idx - half + 1
```

µ=1 时 8 行 → `half=4` → 取后 4 个 rollout，**碰巧正确**；
µ=8 时 64 行 → `half=32` → `keep_from = 7-32+1 = -24` → **8 个 rollout 全进**，"后半程"变成了"全程"；
µ=16 时 128 行 → 同样全进。

所以这个 bug 只在 µ>1 的臂上发作，而 µ>1 正是主结论关心的臂。

| run | 修前 pass | 修后 pass | 差 |
|---|---|---|---|
| mu1_s0 / s1 / s2 | 0.2623 / 0.2656 / 0.2585 | 0.2623 / 0.2656 / 0.2585 | 0 |
| mu8_s0 / s1 / s2 | 0.3516 / 0.3640 / 0.3538 | **0.4290 / 0.4427 / 0.4320** | +0.077 / +0.079 / +0.078 |
| mu16_s0 / s1 / s2 | 0.3886 / 0.3872 / 0.3892 | **0.4883 / 0.4771 / 0.4862** | +0.100 / +0.090 / +0.097 |

**配对差（同 seed）**：

| seed | µ8−µ1 修前 → 修后 | µ16−µ1 修前 → 修后 |
|---|---|---|
| 0 | +0.0893 → **+0.1667** | +0.1263 → **+0.2260** |
| 1 | +0.0984 → **+0.1771** | +0.1216 → **+0.2115** |
| 2 | +0.0953 → **+0.1735** | +0.1307 → **+0.2277** |

这解释了一个此前被当成"两个来源矛盾"的现象：08:10 的记忆条目写 +0.089/+0.126（来自官方脚本），同日验收草稿 §8 写 +0.167/+0.226（来自看板复算）。**看板是对的，官方脚本错了**——讽刺的是同一个 bug 早先在 `dashboard` 里已经修过（commit `d35bedd` "count rollouts, not metric rows"），但 `make_table.py` 没同步。

**影响面**：只有 pass 列与配对差（含 CI）。`d`、`KL`、`clip`、`cost` 都不受影响——它们本来就按 rollout 聚合。

## 3. 缺陷 B（**已修**）：默认命令会被旧探针目录污染

`runs/` 里除了 9 个正式 run，还堆着 `det_*`、`ab_*`、`reg_g4b`、`dryrun`、`hf48g`、`cloud48g_*`。`load_runs` 的键取自**行内的 (arm, seed)**、目录按 `sorted()` 顺序遍历，于是靠后的探针会覆盖靠前的正式 run：

实测执行文档里写的那条命令 `python analysis/make_table.py --runs runs`，得到的 `mu1/s0` 行是：
**1 个 rollout、512 responses、pass 0.2383、d 0.1812** —— 而真的 mu1_s0 是 8 rollout、32768 responses。

顺带一个更隐蔽的后果：`boot_ci` 的 RNG 是全局共享的，键集合一变，**其他臂的置信区间也会跟着漂**（µ8 的 CI 下界从 0.2926 变 0.2930）。

修法：默认 `--pattern "mu*_s*"` 只收 `arm_seed` 命名的目录；同一 (arm, seed) 出现第二次直接**报错退出**，不再静默覆盖。修后 `--runs runs` 的输出与干净子集**逐字节相同**（`diff` 为空）。

**C4 的机制拆解**（数字是实的，解释留给你）：

| arm | d0 | ‖ḡ‖ | σ | σ/‖ḡ‖ |
|---|---|---|---|---|
| µ1 | 0.0689 | 0.00465 | 0.0659 | **14.16** |

## 5. C2 现在可测了（此前记为"不可测"）

之前判"不可测"是因为 `kl_per_rollout_policy` 不在看板 feed 白名单；本地 `metrics.jsonl` 里这个字段是有的。

| run | 相邻 µ-step 上升的对数 | KL@step1 | KL@last | last/1 |
|---|---|---|---|---|
| mu8_s0 | 36 / 56（64%） | 2.73e-5 | 3.09e-4 | 11.3× |
| mu8_s1 | 37 / 56（66%） | −2.28e-5 | 3.36e-4 | 符号翻转 |
| mu8_s2 | 36 / 56（64%） | 2.37e-5 | 3.18e-4 | 13.4× |
| mu16_s0 | 62 / 120（52%） | 3.88e-5 | 5.07e-4 | 13.1× |
| mu16_s1 | 68 / 120（57%） | 5.55e-6 | 4.82e-4 | 86.8× |
| mu16_s2 | 60 / 120（50%） | −1.48e-5 | 3.57e-4 | 符号翻转 |

- 上升比例 50–66%，**和抛硬币没有区别**；能称"monotonish"（≥80% 步上升且净增）的 rollout 只有 4/48。
- **负 KL 每个 run 有 11–29 行**（µ8 11/17/14 行、µ16 29/24/29 行）。精确 KL ≥ 0，负值说明这个量是**采样估计**（k1 类），早期步噪声大于信号。
- 净结论：**跨 rollout 的净增长（µ8 ≈3.2e-4、µ16 ≈4.5e-4，约 11–13 倍于第 1 步）成立；"每个 rollout 内部单调"不成立**。且 µ16 的终值只比 µ8 大 1.4×，**对 µ 是次线性的**——这点比"单调不单调"更值得进报告，但要不要写是你的判断。
